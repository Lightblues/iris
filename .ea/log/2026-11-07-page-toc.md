# 2026-11-07: Table of contents for the page being read

Status: accepted (2026-11-07, D011) with the first option for every question; built in iris-034. Behavior as built: [docs/page-enhancements.md](../docs/page-enhancements.md).

The user wants a table of contents (TOC) on the pages he reads, built from their headings, to jump around in the page without disturbing reading. Two open questions are where it lives and how it behaves.

Reading taken: a TOC of **the page in front of him**, built from its headings (h1 to h6). The other reading, a TOC across the pages he has open, is covered at the end; it does not change the in-page design.

## Where it lives

| Option | For | Against |
|--------|-----|---------|
| A. Side panel tab | No page DOM touched; React and Tailwind already there | Opening the panel narrows the page, which disturbs reading; the panel is enabled per tab and belongs to the agent, so the TOC replaces the chat; panel and page scroll are in different processes, so highlighting the current section needs messages on every scroll |
| B. In-page overlay (content script) | Sits on the page and narrows nothing; scroll and highlight are local and cheap; works on any tab with the panel closed | Injected UI on every site: style clashes (solved by a shadow root), collisions with the site's own TOC or sticky elements |
| C. Both | | Two UIs for one list, for one user |

**Recommendation: B**, an overlay in a shadow root, built in the content script next to the FAB. The side panel gets nothing new; the agent gets the same outline through `read_page` (below).

## Layout

Collapsed by default to a thin rail of ticks at the right edge, vertically centred, above the FAB (bottom-right) so the two never overlap. One tick per heading, length by level, the current section's tick darker. The rail takes no click space beyond about 12 px and never reflows the page.

```
 page text …                                    ─
 page text …                                    ──   ← collapsed rail: one tick per heading,
 page text …                                    ━━     current section darker
 page text …                                    ─
                                                ──
                                                 ◎   FAB (allowlisted sites only)

 hover the rail, or press the shortcut:
                                   ┌ Outline ─────── 📌 ┐
 page text …                       │ 1 Introduction     │  floating card ≈ 260 px, over the page,
 page text …                       │ 2 Method           │  max 70% of viewport height, own scroll
 page text …                       │ ▌ 2.1 Data         │  ← current section
 page text …                       │   2.2 Training     │  h4+ folded under their parent
                                   │ 3 Results        ▸ │
                                   │ [filter…]          │  only when > 40 entries
                                   └────────────────────┘
```

## How the outline is built

- **One extractor**, `lib/outline.ts`, shared by the TOC and `read_page`'s `card` mode (which today takes the first 30 of h1 to h3 on its own). This is the agent tie-in: the agent and the user see the same outline, and AX-3 (one page reader) gets a single heading source.
- **Sources**, in order: `h1`-`h6` and `[role=heading][aria-level]`, visible only (not `display:none`, not zero-size), scoped to `main` / `article` / Readability's content root when one exists, skipping `nav`, `header`, `footer`, `aside`. Empty and duplicate texts dropped; an h1 equal to `document.title` dropped. Levels compressed (a page using only h2 and h4 shows two levels).
- **Shown only when it helps**: at least 3 headings and a page at least 2.5 viewports tall. Otherwise no rail at all.
- **Pages without headings**: no TOC. Guessing from bold paragraphs or font size is noisy; an outline written by the model is the agent's job, asked for in the side panel, not an automatic page feature.
- **Chat sites** (ChatGPT, DeepSeek, Gemini): the chat-export adapters already know the turns, so the TOC can list the user's questions as entries. Optional, see questions.
- **SPA and dynamic pages**: rebuild on the existing URL-change observer in `content/index.ts`, and on DOM mutations debounced to 500 ms, only when the heading list actually changed. Virtualised pages (headings not in the DOM until scrolled to) list only what is rendered; accepted.
- **Long docs**: h1 to h3 shown, deeper levels folded under their parent; a filter box above 40 entries; the card keeps the current entry scrolled into view.
- **Not covered**: Chrome's PDF viewer (not scriptable), cross-origin iframes. The TOC runs in the top frame only.

## Interaction that does not disturb reading

- Nothing opens by itself; no focus or keyboard capture on load; no animation except the active tick moving.
- Hover the rail: the card opens after about 150 ms (so passing the mouse to the scrollbar does not open it) and closes about 300 ms after the mouse leaves. 📌 pins it open for this page.
- Click an entry: scroll so the heading sits just below any fixed or sticky header (measured at jump time), then a short fade highlight on the heading. Smooth scroll for short distances, instant for long ones, instant under `prefers-reduced-motion`. The URL and history are not touched, so SPA routing and Back stay as they were.
- Current section: an IntersectionObserver marks the last heading above the top third of the viewport.
- Keyboard: one extension command toggles the card and focuses it; ↑ / ↓ move, Enter jumps and closes, Esc closes and returns focus to the page. Proposed default `Cmd+Shift+K` / `Ctrl+Shift+K` (rebindable at `chrome://extensions/shortcuts`; Iris uses two of the four suggested keys today). Also a "Toggle outline" row in the command palette.
- Off switch: Settings → Pages → "Page outline: hide on [patterns]", a blocklist like the FAB's (`tocSitePatterns`, synced), for sites with their own TOC (Wikipedia, GitHub, docs sites).
- Colours follow `prefers-color-scheme`, translucent card, so it reads on light and dark pages.

## Fit with existing decisions

- **Conflicts with D006** and the spec's test ("does this make the page agent or the relay better?"), and with page enhancements being "maintain only". A reading TOC is a reading aid, not an entry point. If accepted, record **D011**: reading aids on the page are allowed in Page enhancements when they share code with the agent's page reading (here the outline extractor) and add no new storage or sync. Without that exception the honest answer under D006 is not to build it.
- D003, D010: untouched. D005: one row added under Pages. FAB: unchanged, the rail sits above it. `docs/page-enhancements.md` and `docs/ui.md` get the layout above in the same commit as the code.
- D001: a patch on 0.6.x, or folded into the 0.7 round with AX-3, since both touch `read_page`.

## The other reading: a TOC across open pages

A list of the pages he has open, by title, to jump between them, is what the Tabs view (D010) and Chrome's tab search (`Cmd+Shift+A`) already are. It would live in the side panel or the command palette, not on the page, and needs no new design beyond a "jump to tab" in the existing view. Not proposed unless that was what was meant.
