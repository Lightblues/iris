# 2026-04-23 — Side Panel 冷启动优化尝试

## 问题描述

Iris 的 side panel 打开后出现 **"面板已开但内容迟迟不渲染"** 的现象:
- 触发方式:点扩展图标 / `cmd+shift+O` / `cmd+shift+Y` 都会中招
- 表现:侧边栏窗口本身出现了(有宽度、有边界),里面是一片空白/黑
- 频率:**不是必然**,"有时候挺快的"。在某些时刻、某些环境下特别严重
- **救命操作**:点击页面里的 FAB、或去 `chrome://extensions` 点 `src/sidepanel/index.html` inspect 链接,side panel 就立刻渲染出来

## 环境

- 多显示器
- **标准 Chrome Stable**
- 对照组:Monica 也同样卡 → 倾向 Chrome 系统 bug;但豆包 sidepanel 快 → 可能有 hack 能规避

## 尝试过的方案(按时间顺序)

### 1. 减小 bundle + 骨架屏 + 懒加载

**假设**:bundle 太大,JS parse/eval 慢,导致 React mount 延迟。

**改动**:
- `sidepanel/index.html` 内联骨架屏(tab 条、输入框、加载中动画),明暗主题自适应
- `SidePanelApp.tsx` 把非 Agent tab(SettingsPage / NotesTab / BookmarksTab / ReadingListTab / TabsTab / AgentHistoryTab)改为 `React.lazy`
- OpenTelemetry 改为动态 `import()`,拆 `telemetryState.ts` 让 `createAgent` 不再把整个 otel 拉进主 chunk
- 用 `requestIdleCallback` 延迟 `fetchModels` 和 telemetry 初始化

**结果**:主 chunk 从 547KB → 374KB(gzip 167→115 KB)。**但 side panel 冷启动卡死问题依旧**。

**结论**:bundle 大小不是瓶颈。

### 2. 统一架构到原生 side panel,删除 iframe

**假设**:原先的"FAB 秒开"靠的是常驻 iframe,视觉上快但架构脏;统一到原生 side panel 后应该干净。

**改动**:
- 删除 `content/floatingSidebar.ts` 里的 iframe / resize handle / state 持久化
- FAB 改为 content script → `runtime.sendMessage` → background → `chrome.sidePanel.open({ tabId })`
- 删除 `SidePanelApp.tsx` 的 `isFloatingMode` 检测、`handleClose` 桥接
- 删除 `SidebarHeader.tsx` 的 floating-only 关闭按钮

**结果**:架构干净了,但**这反而移除了"秒开"兜底**,用户抱怨"没法秒开了"。

**结论**:架构正确方向,但失去了 iframe 带来的"永远不冷启动"兜底。

### 3. storage.sync → storage.local 迁移

**假设**:`chrome.storage.sync` 在冷启动路径上挂起,React 的 useEffect 等 `loadSettings()` 返回而挂死 UI。

**改动**:
- `lib/sidepanelSettings.ts` 的 load/save 改用 `storage.local`,加一次性 sync→local 迁移
- `lib/storage.ts`(bookmarks)同样迁移
- `content/floatingSidebar.ts` FAB 站点过滤 local 优先,sync 兜底

**结果**:依旧卡。

**结论**:storage 不是瓶颈,**不过改动本身有价值**(不必依赖跨设备 sync、规避 sync 未知挂起风险),保留不回滚。

### 4. 诊断日志 — 拿到决定性证据

**做法**:在 `main.tsx` 里埋 `[Iris boot] +Nms` 时间戳日志,记录 `main.tsx evaluated / createRoot / first microtask / first setTimeout(0) / first rAF / visibilitychange / focus / blur`。

**卡死状态下的日志**(用户点击 inspect link 救活后才能看到):
```
[Iris boot] +0ms    main.tsx evaluated      · vis=hidden  focus=false
[Iris boot] +3ms    kickPaint(sync)         · vis=hidden
[Iris boot] +3ms    first microtask         · vis=hidden
[Iris boot] +61ms   first setTimeout(0)     · vis=hidden
[Agent] Creating agent...                                        ← JS 一切正常
[Iris] Settings loaded
[Iris boot] +77ms   visibilitychange→visible                     ← 这一刻就是用户点 inspect link 的瞬间
[Iris boot] +169ms  first rAF               · vis=visible        ← rAF 等到 visibility 翻转才触发
```

**决定性证据**:
- 整个 JS 启动链路 **< 100ms 全部完成** —— 代码本身毫无问题
- `visibilityState` 一直卡在 `hidden`,直到外部事件(inspect link / FAB 点击)触发
- `requestAnimationFrame` 在 `hidden` 状态下 **根本不调度**
- Chrome **不向 GPU 提交 frame**,所以屏幕上一直是打开前的那片黑

**根因**: Chrome 的 side panel renderer 启动时 `visibilityState=hidden`,Chrome 不把它翻转为 visible 也不 commit frame,直到某个外部 UI 事件触发。这是 **Chrome 自身的调度行为**,renderer 里的 JS 无法强制让它 commit。

### 5. kickPaint — 尝试强制 commit frame

**假设**:在 renderer 里用常见技巧(reflow、resize event、window.focus())推动 Chrome 提交首帧。

**改动**:`main.tsx` 里每个 rAF tick 调用:
```ts
void document.body.offsetHeight          // 强制 reflow
window.dispatchEvent(new Event('resize'))// 让 Chrome 认为视口变了
window.focus()                           // 把窗口标为 focused
```
在 `visibilitychange=visible` 时再 kick 一次。

**结果**:完全无效。日志显示 kickPaint 被执行了,但 `vis=hidden` 期间 Chrome 仍然不 commit。**根本原因**:这些招数都是在 renderer 内部操作,Chrome 的 `visibilityState` 是只读的,commit 决策在浏览器进程里,renderer 无权干预。

**结论**:从 renderer 侧无法解决。

### 6. 统一 action click 走代码路径

**假设**:`openPanelOnActionClick: true` 让 Chrome 走内部自动路径(慢);而 FAB 路径走代码显式 `sidePanel.open()`(快)。如果把图标点击也改成代码显式调用,应该和 FAB 一样快。

**改动**:
```ts
// 之前
chrome.sidePanel.setPanelBehavior({ openPanelOnActionClick: true })

// 之后
chrome.sidePanel.setPanelBehavior({ openPanelOnActionClick: false })
chrome.action.onClicked.addListener(async (tab) => {
  await chrome.sidePanel.open({ tabId: tab.id })
})
```

**结果**:**依旧卡**。点图标、`cmd+shift+O`、`cmd+shift+Y` 都中招,FAB 仍然是唯一可靠的"救命"入口。

**结论**:假设不成立。"代码主动调 vs Chrome 自动" 不是差异点。

## 当前仍然未解的核心谜团

**为什么 FAB 点击能救活,而图标/快捷键不能?**

三者最终都调用 `chrome.sidePanel.open({ tabId })`,但观察到的差异是系统性的:
- **FAB**(content script → background message → sidePanel.open): **100% 救活**
- **图标 click listener → sidePanel.open**: 卡
- **cmd+shift+Y command listener → sidePanel.open**: 卡
- **cmd+shift+O (Chrome 内置)**: 卡

FAB 路径里"多了什么"?
- content script 是**页面标签页 renderer** 里在运行 —— 那个 renderer **是 focused** 且 **visible**
- user gesture 来源于 **页面本身的 click event**
- 消息要经过 IPC 从 page renderer → SW → 回到我们代码
- 最后 `sidePanel.open` 是**在 SW 里**调用

而 action click / command 的 user gesture 来源于 **Chrome UI 本身**(工具栏图标/键盘快捷键),不来自任何 page renderer。

可能的猜想:**某种 user gesture 来源会影响 Chrome 对 side panel renderer 的 visibility promotion 决策**。来自 page renderer 的 click 传导过来时,Chrome 识别到"有一个活跃的 page context",促使它主动 commit side panel frame;而来自 Chrome 自身 UI 的 gesture,Chrome 认为"我自己的 UI 已经是 active 的了",不急着 commit side panel。

这是推测,没有进一步证据。

## 未尝试的方案

1. **保留 FAB 常驻 iframe 的兜底**:回到更早的架构,FAB 注入 iframe,图标/快捷键开原生 side panel。两套并存,各有利弊。用户明确反对"iframe 脏",所以没走这条。

2. **用户手动点 FAB 当"救命按钮"**:用户本轮提议。代价低,但每次都要动手。

3. **自动检测 + 自动 kick**:side panel 开起来若 N 秒内没 visible,background 自动模拟"触发一次 FAB 路径"把自己救活。实现上可行,但不优雅,而且需要 side panel 与 background 通信确认状态。

4. **chrome.windows.create 独立窗口**:彻底不用 sidePanel API,用独立 popup 窗口。Chrome 对 popup 的 visibility 调度不一样。代价:无法停靠右侧,变成浮动窗口。

5. **Chrome 版本/profile 测试**:换回 Chrome Stable、另一个 profile、关闭多显示器再测。隔离是不是环境问题。

## 2026-04-24 追加实验

用一个最小 repro 插件(112 行 JS,无 React/bundler/storage)在同机器同显示器环境下系统测试。插件在 `experiments/sidepanel-repro/`。

### 确定性结论

1. **这是 Chrome bug,不是 iris 的问题**。repro 插件照样复现:side panel 打开后空白,JS 被冻结。
2. **renderer 的 JS scheduler 被完全冻结**,不只是 rAF。`queueMicrotask` / `setTimeout(0)` 都不跑,直到 `visibilityState` 翻转。`performance.now()` 在 suspend 期间不走(panel 自己"以为"只过了几十 ms,wall clock 过了数秒)。
3. **根因**:Chrome 创建 side panel WebContents 后,不立即提交首帧。首帧提交需要一个新的**用户交互事件**(键盘/鼠标/inspect)来唤醒浏览器进程的 frame 调度。
4. `sidePanel.open()` resolved 和 panel JS 第一行执行之间有 **~4 秒 wall-clock 固定延迟**。这段时间 Chrome 在创建 WebContents + 加载资源 + V8 编译,但不 commit。
5. **多按几次快捷键 / 再点一次 FAB = 立刻 commit**(gap 从 4s→0ms)。说明唤醒条件是"一个新的浏览器进程级 UI 事件"。

### 排除的方向(按实验编号)

| 变体 | 假设 | 结果 |
|---|---|---|
| A baseline(action click) | iris 等价路径 | 复现 ~4s 卡顿 |
| B windows.update({focused:true}) | 多显示器挂错 window | ❌ 无改善 |
| C windowId 代替 tabId | 参数影响挂载行为 | ❌ 无改善 |
| D FAB(content→SW→open) | gesture 来源影响 | ❌ 同样卡 ~4s |
| E 同 tick 连发 open ×3 | Chrome rush 路径 | ❌ Chrome 视为一次操作 |
| F setTimeout 1s nudge | SW 自动 re-open | ❌ throw "user gesture required" |
| G 双 nudge 700ms+1500ms | 同 F | ❌ 同 F |
| H content script rAF compositor wake | page compositor 活跃带动 panel | ❌ page 和 panel compositor 隔离 |
| Prewarm hidden iframe | 预热 V8 code cache | ❌ 加速了 SW roundtrip(156ms),但不影响 WebContents 首帧 commit |

### 关键发现:什么有效

- **第二次用户交互**:已打开的 panel 在空白状态时,用户再按一次快捷键、点 FAB、或点 inspect,panel 立刻(<50ms)commit 首帧
- 这是唯一稳定有效的路径
- 从 SW / content script 无法模拟(sidePanel.open 需要 gesture;page compositor 和 panel compositor 隔离)

### 当前决策

**接受 Chrome 的行为,不再尝试从扩展侧绕过**。具体:
- 快捷键/图标打开后若空白,用户**多按一次快捷键**即可
- FAB 路径作为最可靠入口(用户在页面上操作 → compositor 活跃 → commit 更快)
- 不回滚任何已做的优化(bundle 减小、storage.local、骨架屏仍有价值)
- 保留 repro 插件供未来 Chrome 版本回归测试
